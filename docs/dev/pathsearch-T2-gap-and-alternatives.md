# PS-T2 — Realtime per-keystroke `<50 ms` path FTS: the gap & every alternative

**Owner:** `ps-t2-alts` (team `bitmagnet-bench`, task #73) · **Date:** 2026-06-09 · **Status:** READ-ONLY analysis (no prod changes, no new bench runs — any new measurement is _proposed gated_, not run).
**Source of truth:** `/Users/me/aaa/github/bitmagnet` code + the measured suite. Measured numbers cited from [`arch-c-parity-and-optimization-results.md`](./arch-c-parity-and-optimization-results.md) and [`cjk-tokenizer-and-incremental-merge-bench-RESULTS.md`](./cjk-tokenizer-and-incremental-merge-bench-RESULTS.md) (= EXP-D / D2 / E). ## 0. TL;DR

- **The requirement is _infix/substring_, not prefix.** Paths are not word-segmented prose; the workload is "find `1080p` / `S01E` / `电影` _anywhere_ in a path." This single fact demotes the prefix-typeahead engines (Meilisearch, Typesense-default, Algolia-style): their "per-keystroke typeahead" core competency is **prefix-of-token**, which is _not_ our query shape. To do mid-path substring they must index all suffixes/ngrams — i.e. pay the **same postings cost we already measured**.
- **The `~+90 GB` cost is intrinsic to CJK-correct substring, not a hand-rolled artifact.** EXP-D: the only thing that fixes CJK substring is a **char n-gram** tokenizer (default recall **0.0037** → ngram **1.0**), and ngram postings blow the path field **21.5 → 103 B/doc (~4.8×) → ~+90 GB @ 879.5 M** — almost entirely postings. _Every_ engine that does CJK substring pays this (it is postings math). External engines **relocate** the cost (RAM / JVM heap / object store) and **add a service**; none make it cheap.
- **Only a _local_ mmap inverted index measured `<50 ms` per-keystroke** (EXP-D2: selective CJK warm p50 **0.07 ms** / cold 0.86 ms). Object-store engines (Quickwit) are sub-second-not-sub-50ms; fully in-RAM engines (Typesense) at 879 M docs need ~hundreds of GB RAM = infeasible here.
- **Honest caveat on the bar itself:** even the inverted ngram index is **not** `<50 ms` on the _broadest short_ queries — EXP-D2 broad ASCII grams (5.6 M hits) **p50 100–145 ms / p95 244–320 ms**; live un-merged index ext∧size **~40–46 ms** (EXP-E). `<50 ms` holds for **selective** queries; the broadest 1–2-char prefixes are the latency ceiling on _any_ engine (match-set size is intrinsic). Still **100–160× faster than DuckDB-ILIKE's ~23 s**. Closing that broad-prefix gap (min query length, debounce, top-k early-term, prefix match-set caps) is **PS-T3's** problem; T2 only surfaces it.
- **Verdict:** a **hand-rolled Tantivy char-ngram index is genuinely the best fit for the stated bar** — but the decisive reason is that the cost is engine-independent and we already own the hard part (a CJK-correct writer+query-parity tokenizer). The single strongest _external_ alternative worth a real look is **Manticore Search** (single binary, mature realtime infix) — named below with its caveats. The overriding recommendation is unchanged: **gate the whole index (any flavor) on a hard, measured product need** — DuckDB-on-Parquet already covers structured per-file search (+3.9–12.3 GB, <250 ms) and non-realtime path-FTS (ILIKE 142 ms paginated / DuckDB-FTS ~150 ms).

## 1. The gap — what _cannot_ serve realtime per-keystroke `<50 ms` free-text path search

Grounded in the deployed code + the decided architecture (`per-file-search-master-design-and-results.md` §3, §5):

- **Main search is DROP-independent** and runs on `torrent_contents` (PG `tsv` + `ts_rank_cd`), never on `torrent_files` — so it is _not_ the thing in question. Per-file path free-text is a **net-new** capability that `torrent_files` never served either (its only live read is the `extension IN (…) EXISTS` filter, `criteria_torrent_file_extension.go:24-34`).
- After the (deferred) `DROP TABLE torrent_files`, the per-file path string lives **only in the per-torrent `files_data` blob** (zstd+msgpack, `BlobFile{i,p,e,s}`, `blob.rs:31-46`). Any path-search engine must build its structure **out of the blob** (or out of Parquet exported from it). They therefore all _survive the DROP equally_ — the blob is the post-DROP source of truth.
- The differentiator is **latency × CJK-correctness × ops-cost × disk**, _not_ "can it survive the DROP."

So the gap is narrow and specific: **interactive (`<50 ms`), per-keystroke, free-text _substring_ path search that is CJK-correct.** Everything else about per-file search is already cheap on DuckDB-on-Parquet.

## 3. Why each non-engine option fails the bar (detail)

- **(a) PG ILIKE — moot + slow.** Measured **23–27 s** for COUNT/no-LIMIT, leading-wildcard is unprunable (ARCH-C §1, row 1b). Fast _only_ for common-substring + LIMIT early-out (79 ms). And it reads `torrent_files`, which is being dropped — so post-cutover it doesn't exist. Not a realtime path.
- **(b) DuckDB-FTS/BM25 — the cheap non-CJK answer, but not per-keystroke-CJK.** `23 s → 147–186 ms` at **+34.9 GB** (ARCH-C §3). But it is **token-match, no CJK segmentation** — it matched the exact `电影` token by luck in the bench; a sub-token CJK query misses (ARCH-C §3 note). Freshness is batch (immutable read-only generations). Good enough for _non-realtime ASCII_ path search; does not clear the CJK `<50 ms` bar.
- **(c) JSONB / agg — not free-text.** `file_extensions @>` and `agg_torrent_ext` answer _presence_ of an extension (the DROP-gate filter/facet); they carry no path tokens. N/A.
- **(d) blob decode — wrong granularity.** Decode is **0.6–0.94 µs/file** but it is _per-torrent_ (browse/hydration). There is no cross-corpus per-keystroke shape here.
- **(e) pg_trgm GIN — three independent disqualifiers.** (1) **CJK-broken for short queries:** trigrams need ≥3 chars; 1–2-char CJK per-keystroke returns nothing, and `pg_trgm` needs a non-`C` locale to handle wide chars at all [web]. (2) **No-trigram patterns degenerate to a full-index scan** [web] — exactly the short-prefix regime. (3) **Survival:** the path string lives only in the blob post-DROP, so pg*trgm needs its **own** path column/table (re-materialize ~261 GB of path rows, or a slim path table) — re-introducing a large object on the PG node this whole effort exists to shrink. It loses on cost, CJK, \_and* the DROP. (Not benchmarked — and not worth a gated run given the structural disqualifiers; if anyone insists, a gated `pg_trgm` smoke on the HEL1 restore is the only honest way to size the GIN, but I recommend against spending the run.)

## 4. Hand-rolled Tantivy vs external engines — the honest weigh-up

**What "hand-rolled" actually means here (correcting a common conflation):** the existing `feat/tantivy-search-sidecar` is a **torrent-grained MAIN-search** replica of PG FTS — its tokenizer (`tokenizer.rs`) replicates Go `TokenizeFlat` _byte-for-byte_ (transliteration + one-token-per-CJK-rune via go-unidecode), which is the **PG-FTS-parity word tokenizer, NOT a char-ngram path tokenizer.** So we do **not** have production per-file _path_ search code. What we _do_ have is (i) the **bench-proven** `bench-file-index` ngram crate (EXP-D/D2/E), and (ii) a mature Rust **search-sidecar skeleton** (schema/index/server/gRPC) + the CJK tokenizer _infrastructure_ to extend. Building L3 = adding an ngram path field/index to that skeleton, not greenfield.

**The case _for_ hand-rolled (for the stated bar):**

1. **The +90 GB cost is engine-independent** (postings math, EXP-D) — so no external engine undercuts it; they can only move it (Quickwit→object store, Typesense→RAM, OpenSearch→heap) and add a service.
2. **We already own the hard part.** The #1 way external Tantivy-based engines fail CJK is the **QueryParser tokenizes the query as English before the field tokenizer runs** (tantivy #718, hits Quickwit) [web]. Our `tokenizer.rs` already registers **one** tokenizer for _both_ writer and query parser — the exact fix — and we have a writer/query-parity test harness + fixtures. The ngram crate already proved recall/precision **1.0**.
3. **Lowest _added_ ops surface:** it embeds in the Rust sidecar we are already deploying for DuckDB/search — no new cluster, no JVM heap, no separate RAM budget. Disk-backed mmap (not Typesense's all-RAM, which is infeasible at 879 M docs).
4. **Only it measured the bar:** local mmap, selective CJK **0.07 ms** warm / 0.86 ms cold, **~2 ms** freshness with bounded segments (EXP-D2/E). Object-store and RAM engines either miss `<50 ms` or miss the RAM budget.

**The case _against_ / strongest external alternative:**

- **Manticore Search is the one external worth a real spike** _if_ the org values buying ops-simplicity over maintaining Rust index code. Single binary, mature realtime index, and its **keywords-dict `min_infix_len`** claims **+1–10% disk** (not +90 GB) via search-time wildcard expansion rather than pre-indexed substrings [web]. **But** its caveats bite exactly where it matters: (i) **query-time wildcard expansion blows up on broad/CJK infixes** (needs `expansion_limit`) — i.e. it's weakest in the broad-short-prefix regime that is _already_ the latency ceiling; (ii) **1-gram-only CJK** charset (vs our bi/tri-gram measured at recall/precision 1.0) — likely lower precision on 2–3-char CJK; (iii) it's an **unproven new dependency** against our **measured** numbers. The +1–10% claim is for _Latin_ infix; CJK 1-gram + wildcard expansion is a different cost curve we have **not** measured. Recommendation: if ops-cost is judged to dominate, **propose a gated Manticore spike** (build the path index on the HEL1 restore, measure disk + broad/selective/CJK latency) before committing — don't adopt on the brochure number.
- **Quickwit** (runner-up) is _literally Tantivy_ — same CJK story we've solved — and uniquely lets the +90 GB live on **cheap object storage**, distributed and battle-tested (Datadog). But object-store query latency is **sub-second, not sub-50 ms cold**, so it fails per-keystroke unless heavily cached; and it adds a distributed service tuned for logs. Good fit only if the requirement relaxes from `<50 ms` to "interactive seconds at scale on cheap storage."
- **Meilisearch / Typesense** are the wrong tool: **prefix-first**, infix is unsupported (Meili) or expensive opt-in (Typesense), and Typesense's all-RAM model is **infeasible at 879 M docs** (~14 GB RAM per 28 M books → hundreds of GB). They shine for _prefix typeahead over small corpora_, which is not this.
- **OpenSearch/ES ngram** is the most ops-heavy and explicitly anti-recommended for ngram bloat [web]. Only consider if the org already runs an ES cluster.

## 5. Verdict

**Is a hand-rolled inverted ngram index the _only/best_ way to get realtime per-keystroke `<50 ms` CJK-correct path FTS?**

- **Best for the stated bar: yes, narrowly** — but the honest reason is _not_ "hand-rolled is magic." It is that **(1)** the dominant cost (~+90 GB postings) is **intrinsic to CJK substring and engine-independent**, so no external engine beats it on cost; **(2)** the local mmap Tantivy path is the **only one measured to hit `<50 ms`** (selective); **(3)** we **already own** the CJK writer+query-parity tokenizer that is the single hardest, most-commonly-botched piece; and **(4)** it adds the **least new ops surface** (embeds in the sidecar we already run).
- **Not the _only_ way, and `<50 ms` is not flatly achievable:** even the inverted index is **100–320 ms on the broadest short prefixes** — that ceiling is intrinsic to match-set size and is **PS-T3's** tension to solve (min query length, debounce, top-k early-termination, prefix caps), not something a different engine removes.
- **Single strongest alternative to hand-rolled:** **Manticore Search** — _if and only if_ ops-cost is judged to outweigh CJK fidelity and the value of our measured numbers, and _after_ a gated spike validates its CJK-infix disk+latency (its +1–10% claim is Latin-only and unmeasured for our corpus). Otherwise **none** — the external engines either relocate the same cost while adding a service (Quickwit/OpenSearch), miss the realtime/RAM budget (Quickwit object store / Typesense all-RAM), or don't do mid-path substring at all (Meilisearch).
- **Overriding recommendation (unchanged from the suite):** **gate the entire index — any flavor — on a hard, measured product need for interactive CJK free-text path search.** Until then, DuckDB-on-Parquet covers structured per-file search (+3.9–12.3 GB, <250 ms) and non-realtime ASCII path-FTS (ILIKE 142 ms paginated / DuckDB-FTS ~150 ms at +35 GB). The CJK ngram index nearly triples the replacement footprint (−93% → −55% savings vs the dropped 276 GB) — it must earn its keep against a real `<50 ms`-CJK-per-keystroke requirement, not be built by default.

**Proposed (gated, not run) measurements, if a decision needs them:** (1) a Manticore CJK-infix spike on the HEL1 restore (disk + broad/selective/CJK latency vs our Tantivy numbers); (2) a broad-short-prefix latency sweep on the existing ngram index to size the PS-T3 mitigations. Both are read-only on the throwaway HEL1 restore; neither touches production.
